This is the first release candidate for SoiréeHost 1.0. It is also the first release, so everything below is new. It is a pre-release: expect problems, and please report them.

SoiréeHost puts a website or an app from your Windows PC on the internet through Cloudflare Tunnel. Your PC opens the connection outwards. No port is opened on your router or PC, and visitors do not learn your home IP address.

## Platform

Windows 11 x64 only. Other Windows versions are not tested or supported. Installing, repairing, updating and uninstalling need administrator permission.

## What 1.0 includes

- One program, `soireehost.exe`, with an install window and an uninstall entry in Windows Settings.
- Publish a folder of web files, or an app that runs on your PC.
- A temporary `trycloudflare.com` link with no account, for up to four sites at once.
- A permanent address on your own domain, through your own Cloudflare tunnel (see the known limits).
- For each site: a web application firewall (OWASP Core Rule Set) that blocks attacks by default, a rate limit, an upload limit and security headers.
- Refusal to publish system and profile folders. Hidden files, private keys and backups in a site folder are not served.
- A control panel with an activity list, a security page, a change history, settings export and import, and earlier versions of your settings.
- One switch that takes everything offline.
- The part that handles internet traffic runs boxed in, under its own Windows account, with no access to secrets or settings.
- A daily update check on GitHub, which you can turn off. An update installs only if it is signed with the project's update key and is newer than your version.
- No telemetry. The only outbound connections are the tunnel and the update check.

SoiréeHost protects the way in to a hosted app and limits the damage if the app is broken into. It cannot fix flaws inside the app you host.

The [user guide](https://github.com/TheAlsaadi/SoireeHost/blob/v1.0.0-rc.1/docs/USER_GUIDE.md) covers each step.

## Download and verify

Download `soireehost.exe` and `SHA256SUMS` from this page.

**`soireehost.exe` is not Authenticode-signed yet.** The project plans to apply for free code signing through the SignPath Foundation after its first release. Until then, Windows SmartScreen may warn you ("More info", then "Run anyway"). Check the file first.

1. Compare its hash with the `soireehost.exe` line in `SHA256SUMS`. The letters may differ in case.

   ```powershell
   (Get-FileHash .\soireehost.exe).Hash
   ```

2. With the GitHub CLI, check the build provenance attestation. It shows that this repository's CI built the file.

   ```powershell
   gh attestation verify soireehost.exe --repo TheAlsaadi/SoireeHost
   ```

`manifest.json` is the signed update manifest. It holds the version, size and SHA-256 of `soireehost.exe`, signed with the update key `229bc25eefe83c4a`. An installed SoiréeHost checks that signature before it installs an update. It does not check your first download, so use the two steps above for that.

The release also holds two software bills of materials (`soireehost.cdx.json` and `frontend.cdx.json`).

## Updates from a release candidate

A release candidate is offered the next full release, not later candidates. To move to a later candidate, download it and run it over this one.

Until a full release exists, there is nothing for this candidate to find. An update check then reports "Could not reach GitHub". This is expected.

## Known limits

- **A permanent address with a tunnel token has not been verified with a real hostname.** It is built and tested with a stand-in only.
- **No independent security review or paid audit has been done.** The project is built by one person. Reviews are welcome. Please report security problems privately, as [SECURITY.md](https://github.com/TheAlsaadi/SoireeHost/blob/v1.0.0-rc.1/SECURITY.md) describes, not in a public issue.
- **Private sites (Cloudflare Access) are not part of 1.0** (requirement S-17). The app offers no such option. Every site you publish is public.
- **Quick share links are temporary.** The address changes whenever the tunnel restarts.

## Known issues

Seven findings of Medium severity in the code are open. They come from the project's own [review of 12 November 2026](https://github.com/TheAlsaadi/SoireeHost/blob/v1.0.0-rc.1/docs/reviews/2026-11-12-skills-review.md). They will be fixed before 1.0.0. Most are internal functions that are easy to misuse in a future change. The review records no attack path for an open item beyond what its description says; most need code already running as an administrator, SYSTEM or one of SoiréeHost's own services.

| ID | Problem |
| --- | --- |
| SE-02 | The internal function `DropPrivileges` keeps the Windows privileges it is given and removes all others. Its name suggests the opposite, so a future caller could get it wrong. |
| SE-04 | The internal functions that apply folder permissions do not treat the same permission string the same way. A string with missing or unprotected parts is handled differently by each. |
| SE-06 | The function that gives SoiréeHost's services access to a site folder takes the two service identities as plain text. If they were swapped by mistake in the code, it would still build, and the supervisor service could read every file of a site. |
| SE-08 | An internal function that resets file permissions skips files that have more than one hard link. Only tests use it today. It reports the skip in a way that is easy to ignore. The link check and the change open the file separately, so the file could be swapped in between. |
| SE-09 | The check of who may write to a file or folder looks only at that object and follows links. It does not check whether someone could replace it through a parent folder. |
| SE-13 | The change history is chained, but not with a secret key. Someone who can write the file could cut off its end, delete it, or rewrite it all, and it would still pass the check. When a broken chain is found, the log still opens without an error, and a caller must check the report. The user guide's statement that the history "cannot be rewritten" is too strong. |
| SE-15 | Nothing in the code stops a secret from being written into a change history entry. Only a comment forbids it. The entry's actor and action are plain text that could be swapped by mistake. |

One more problem, UPD-1, can make an update fail when it should succeed. This is rare: it needs SoiréeHost's background service to have failed and restarted in the minute before the update. If it happens, setup reports that the update was rolled back. Your previous version and settings are put back as they were. Installing the update again works. It will be fixed in the next release.

Lower-severity findings and gaps in the tests are listed in [docs/HISTORY.md](https://github.com/TheAlsaadi/SoireeHost/blob/v1.0.0-rc.1/docs/HISTORY.md) and the reviews.

## Reporting problems

For a security problem, use the private route in [SECURITY.md](https://github.com/TheAlsaadi/SoireeHost/blob/v1.0.0-rc.1/SECURITY.md). For anything else, open an issue with your SoiréeHost version (Settings > About), your Windows version and the steps that cause it.
